# 需求澄清清单（五维归类）

> 输入：PM 一句话需求"已有公司官网骨架，需要补充一批演示用的工程文档"  
> 来源 Skill：`req-clarify`  
> 状态：定稿 v1

## Who（角色与干系人）

- Q-W-001：本批文档面向哪些读者？（候选：PM、前后端、测试、运维、新人）
- Q-W-002：是否需要对外发布（GitHub Pages / 内网 Wiki）还是仅在仓库内归档？
- Q-W-003：评审角色是否包含安全（SecOps）与法务？

## What（范围与产物）

- Q-WT-001：本次产出物覆盖几个阶段？（确认：需求 / 设计 / 开发 / 评审 / 测试 / 发布 / 监控 / 排障 共 8 个）
- Q-WT-002：是否包含反面教材（`bad-samples/`）？
- Q-WT-003：示例数据规模？（确认：4 分类 / 8 产品 / 5 新闻 / 11 评论）

## Why（目标与价值）

- Q-WY-001：本批文档要达成的核心目标是"教学可读"还是"贴近真实生产"？（答：以教学为先，但所有产物必须能被对应 Skill 重新生成）
- Q-WY-002：是否要给读者提供"可一键复跑"的脚本？（答：是，`docker compose up --build`）

## When（时间约束）

- Q-WH-001：交付节奏？（确认：随书章节同步，每章对应一个阶段）
- Q-WH-002：示例工程的演示版本号锚定哪一版？（答：v0.2.0）

## How（实现方式与约束）

- Q-H-001：技术栈是否锁定 Next.js + FastAPI + PostgreSQL？（答：是）
- Q-H-002：所有产物是否必须落到 `outputs/0X-*/` 目录？（答：是，子目录与阶段一一对应）
- Q-H-003：是否允许产物里出现 TODO / 占位符？（答：不允许，每个文件要能独立阅读）
