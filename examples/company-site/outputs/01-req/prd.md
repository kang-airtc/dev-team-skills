# company-site PRD v0.2.0

> 来源 Skill：`req-prd`  
> 输入：`clarify.md` + PM 一句话需求  
> 状态：已通过 `design-review` 多角色评审

## 1. 背景

公司官网长期由静态页面拼装而成，缺少后台、缺少结构化内容管理、缺少演示用的工程产物。本次迭代在保留现有公开站观感的前提下，重写为前后端分离架构（Next.js + FastAPI + PostgreSQL），并补齐 8 个阶段的完整产出物，作为本书第 14 章的示例工程。

## 2. 目标

- 公开站：首页 / 关于 / 产品 / 新闻 / 联系 5 类页面可正常浏览
- 后台：管理员可对分类、产品、新闻、评论做 CRUD
- 工程产物：随代码落盘的需求、设计、评审、测试、发布、监控、排障文档可被对应 Skill 重新生成
- 一键启动：`docker compose up --build` 后所有服务进入可用状态

## 3. 非目标

- 不做多语言、多租户、SSO、A/B 实验
- 不做支付、订单、库存等电商重逻辑
- 不接入第三方监控 SaaS（自带的 `monitor-*` Skill 已够用）

## 4. 用例

### UC-PROD-001 创建产品

- 角色：管理员
- 前置：已登录后台
- 步骤：
  1. 进入「产品管理」点击「新建」
  2. 填写名称、价格、分类、封面图、图集（可多张）、规格 JSON
  3. 提交
- 后置：产品状态为「草稿」，待"上架"操作后公开站可见
- 异常：
  - 名称重复 → 1004 业务异常
  - 封面缺失 → 前端校验拦截

### UC-PROD-002 上下架产品

- 角色：管理员
- 前置：产品已存在
- 步骤：在产品列表行内点击「上架」/「下架」开关
- 后置：`is_published` 字段切换，公开站列表/详情立即反映

### UC-NEWS-001 发布新闻

- 角色：管理员
- 步骤：新建新闻 → 编辑正文 → 设置发布时间 → 提交
- 后置：到达发布时间后公开站可见

### UC-COMM-001 用户发表评论

- 角色：匿名访客
- 前置：进入产品详情页或新闻详情页
- 步骤：填写昵称、邮箱、内容 → 提交
- 后置：评论以"待审核"状态保存，admin 在后台可"显示/隐藏"
- 异常：内容空 / 长度超 1000 字 → 前端拦截

### UC-UPL-001 单图上传

- 角色：管理员
- 步骤：在表单点击上传按钮 → 选择本地图片
- 约束：MIME ∈ {jpeg, png, webp, gif}，体积 ≤ 5 MB
- 后置：返回相对 URL，前端拼接 `NEXT_PUBLIC_API_URL` 渲染

## 5. 数据模型

`users / categories / products / news / comments` 五张表。`comments.target_type` 同时支持 `product` 与 `news`，多态关联。

## 6. 接口约定

- 所有 API 走统一前缀 `/api`
- 响应包装 `{code: int, msg: str, data: T}`
- 业务错误走 `HTTP 200 + code≠0`（如 1004 表示业务校验失败）
- HTTP 4xx/5xx 仅留给网关层与未捕获异常
- 鉴权使用 JWT，access token 30 分钟，refresh token 7 天

## 7. 里程碑

| 里程碑 | 内容 | 周期 |
|---|---|---|
| M1 | 数据模型 + 鉴权 + 上传 | 第 1 周 |
| M2 | 产品 CRUD + 公开站列表/详情 | 第 2 周 |
| M3 | 新闻 + 评论 + 后台审核 | 第 3 周 |
| M4 | 工程文档全套落盘 + 发布 v0.2.0 | 第 4 周 |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 评论多态字段查询慢 | 列表页延迟 | `(target_type, target_id)` 复合索引 |
| 上传目录爆盘 | 服务不可用 | 5 MB 上限 + `monitor-containers` 容量告警 |
| AI 生成代码不符合规范 | 评审打回多 | `review-backend` / `review-frontend` 在合并前硬卡 |
